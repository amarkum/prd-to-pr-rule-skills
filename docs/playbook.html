1

The recommendation

  1. Use the agent runtimes you already have as the platform. Claude Code and Cursor already provide sandboxing, permissions, subagents, hooks, MCP connectors and headless CI. Package the process as one versioned plugin repository that both tools install. Build a custom orchestrator later, and only if volume or cross-repo coordination demands it.
  2. Three human gates, enforced by code. The PRD is ready (the product owner has answered the questions), the spec is approved (by the tech lead), and the PR is merged (by code owners). Agents do the work between the gates. Hooks stop them from skipping a gate or approving their own spec.
  3. One builder, specialised per repo. Each repo declares its stack, commands and contracts in .ai/repo.yaml, and stack skills load automatically by file path. The same builder writes a DAG in the data repo and a component in the micro-frontend, following each repo's conventions.
  4. Evidence is computed, not claimed. Tests are named after acceptance criteria. A script proves that each new test fails without the change. CI re-runs everything at the PR's commit, hashes and attests the artifacts, and posts the verdict on the PR.
  5. Knowledge compounds through pull requests. Every lesson becomes a reviewed entry with an owner and an expiry date. A lesson that recurs becomes a rule, and then an automated check.
  6. Start small and measure. Spend two weeks on Setup B (section 11) with one repo per stack. Compare lead time, rework and escaped defects with the last 20 comparable tickets before automating any triggers.

It invests in infrastructure before proving the workflow, and leaves the artifacts undefined: where rules live, how they reach developers, what makes evidence credible. Rules of thumb

  • Must always hold: a hook or a CI check. Prose is advice; hooks are enforcement.
  • Needed for some tasks: a skill, with paths if it concerns certain files.
  • A fact about this repo: AGENTS.md for people, .ai/repo.yaml for machines.
  • Live data: a connector, read-only, local or dev only.
  • Must reach every developer and stay current: put it in the plugin and version it.
  • A judgement call: a subagent with the right tools, then a human gate.

One builder, three repos

The builder is a single agent persona with an engineering discipline: test-first, small commits, stop when stuck. Its stack expertise comes from versioned packs that the repo selects, so it never has to remember three sets of conventions. A developer who mostly writes React can ship an Airflow change with the same guardrails, because the Airflow conventions, tests and checks arrive with the repo.

How the specialisation happens

  • The manifest. .ai/repo.yaml declares the stack, the check commands, the test runner for given files, JUnit paths and protected paths. Hooks, scripts, agents and CI all read the same file.
  • Session context. At start, resume and after compaction, the sdlc-core SessionStart hook injects the stack, the checks, the branch's Jira key, the spec status and the evidence status, plus the always-on rules.
  • Path-activated stack skills. airflow-dag declares paths: dags/**, include/**, so it loads when the builder touches DAG code, in Claude Code and in Cursor alike. stack-mfe depends on stack-frontend, so an MFE repo gets both.
  • The builder subagent reads the manifest and loads the stack skill before every task. To make the builder the main session, start Claude Code with claude --agent sdlc-core:builder.

Stories that span repos

The spec's "Repo impact and sequencing" table sets the order: producers before consumers, each step backward compatible and safe to deploy alone. Each repo gets its own branch, evidence and draft PR, all linked to one Jira epic. The spec is approved once, in the lead repo; the other branches carry a copy with a canonical: link. evidence.py reads the spec's table to decide which ACs each repo must cover, so the MFE's PR is judged only on AC-1, 3, 4, 6 and 7.

The PRD gate: reporting gaps to the product owner

What is checked

Deterministically, with prd_lint.py, the same way every time:

  • 15 sections, 9 of them required: summary, problem, goals, non-goals, users and roles, functional requirements, acceptance criteria, NFRs and open questions.
  • Placeholders (TBD, <name>, "to be decided"), empty sections, and N/A where it needs confirming.
  • Acceptance criteria written as Given/When/Then, and every FR covered by an AC.
  • Vague terms ("fast", "intuitive", "real-time") on lines without a number.
  • NFRs about performance, freshness or availability without numbers.
  • No error, empty or no-access states described.
  • Unresolved open questions, which block unless tagged [non-blocking].

With judgement, by the read-only prd-analyst subagent against a rubric: contradictions, roles and data scope, unhappy paths for UI and pipelines, data feasibility against schema snapshots, hidden cross-team scope, and known production incidents in the area.

The loop

  1. The product owner adds the label prd-ready. Confluence Automation's "Page labeled" trigger sends a web request to GitHub repository_dispatch (event prd-ready, payload with the page id and Jira key).
  2. ai-prd-intake.yml fetches the page version as Markdown (atlassian.py page-md), lints it, and runs the prd-review skill headlessly. A --json-schema forces a typed verdict.
  3. NEEDS_CLARIFICATION: the workflow adds a Confluence footer comment with the questions, creates a "Clarify PRD" Jira task for the product owner, and moves the epic to Needs Clarification.
  4. READY: context and a draft spec are produced and opened as a draft spec PR for the tech lead.
  5. A new page version re-runs the gate, and the new review lists what was "Resolved since version N".

WhyA product owner should get one consolidated, plain-language list with suggested defaults to accept, not a chain of chat threads. The clarification reasons are recorded, and they feed the PRD template and product-owner coaching (section 10).

Rules that keep this safe

  • Snapshots first. Committed JSON Schema snapshots in docs/schemas/ are reviewed and diffable. Live MCP covers only what they lack. schema_snapshot.py samples to a file, so record values never enter the conversation, and diff exits 1 on a breaking change.
  • Read-only at two levels: the server flag (--readOnly, readonly = true, AF_READ_ONLY) and a read-only database user. The shell hook also blocks writes through mongosh and psql.
  • Untrusted content. PRDs, tickets, logs and rows are data, never instructions. This addresses the "lethal trifecta" (private data, untrusted content and a way out) and Meta's "Rule of Two": the research stages read; the build stage writes code but has no outbound channel except git push to its own branch; PR creation is gated; a human merges.
  • Prefer CLIs for git, gh and test runners. They cost less context and behave deterministically. Thoughtworks lists "MCP by default" under Caution.
8

Specs that drive the build

The PRD says what and why; the spec says how, precisely enough that build, verify and review can be checked against it. It lives in git as specs/<KEY>/spec.md and is reviewed like code.

  • Traceable IDs. FR-n requirements from the PRD; AC-n criteria in Given/When/Then, each citing its FRs.
  • Design only where something changes: data (before and after, indexes, compatibility), pipeline tasks, contracts (API, exposed modules, events), UI states.
  • A repo impact and sequencing table that tooling reads: order, repo, change, ACs, backward compatibility.
  • A test plan giving the level, the qualified test name (PAY-412 AC-3: ...) and the repo for every AC.
  • A risk tier: low, medium, or high (auth, PII, migrations, money). A high tier lists the extra approvals it needs.
  • Open questions must read "None." before approval.

Approval is human and enforced. The edit hook refuses any agent edit that sets status: approved, and refuses code changes on a branch whose spec is still a draft. The eval suite measured the difference: asked to implement against a draft spec, the agent stopped and explained the approval step with the plugin (score 1.0), and wrote the code anyway without it (0.5).

Fast laneSpec-driven development is criticised for applying one heavy process to every change (Böckeler turned a small bug into 4 user stories and 16 ACs). Low-risk changes in one repo with no data, contract or auth impact use a short spec: summary, ACs, repo impact and test plan. Ceremony scales with risk; the gates don't.

Credible evidence: how tests prove the change

An agent saying "all tests pass" is not evidence. Green CI isn't enough either: public benchmarks found that 15–28% of "passing" patches were wrong because the tests were weak, and models under pressure modify tests to pass. The protocol below makes the claim checkable.

LevelWhat it isAccepted for
L0 ClaimedThe agent says it worksNothing
L1 Localevidence.py run at a committed SHA: checks with logs and SHA-256 hashes, AC coverage, fail-to-passOpening a draft PR (the hook checks it)
L2 CIThe same script on a clean runner at the PR head SHA, plus changed-line coverage; artifacts uploaded; sticky PR commentReview and merge (a required check)
L3 AttestedThe L2 artifacts signed with actions/attest@v4 (Sigstore provenance bound to commit and workflow)Audit and regulated changes

The protocol

  1. Tests cite acceptance criteria by qualified ID: it("PAY-412 AC-3: ...") or test_pay_412_ac_3_.... ac_coverage.py reads JUnit from pytest, Vitest, Jest and Playwright, and marks each AC covered, failing, manual or missing. The Jira key keeps AC-3 of one story from matching another's.
  2. Fail-to-pass, after SWE-bench: fail_to_pass.py copies the new tests onto the merge-base in a temporary worktree. Each must fail there and pass on the branch. A test that passes on both doesn't prove the change; one that only errors on import counts as weak.
  3. No silent weakening. The edit hook refuses new skip, only, xfail and fixme markers unless the line carries a justification, and refuses hand edits to .ai/evidence/.
  4. An independent check. The read-only qa-verifier judges whether each AC test asserts the outcome, avoids tautologies, doesn't mock the unit under test, and covers unhappy paths.
  5. Binding to code. The manifest records the head SHA, the merge-base, the spec's hash and status, the runner and the CI run URL. The PR gate rejects stale evidence (HEAD moved) and dirty trees.

Compounding knowledge

Every story should make the next one easier. The learn skill runs after review or merge. It collects review comments, rework commits, CI failures, PRD clarification rounds and linked incidents, and proposes changes through a reviewed PR. A lesson moves up a ladder each time it recurs; each rung enforces it more strictly.

RUNG 0

Observation

A review comment, a CI failure, an incident, a PRD clarification

RUNG 1

Knowledge entry

Reviewed, owned and dated; agents find it when it's relevant (knowledge/)

RUNG 2

Rule or skill text

Loaded every session, or on matching paths

RUNG 3

Hook, lint or test

Enforced deterministically. If a reviewer has said it twice, it belongs here.

Lesson typeDestinationOwner
Fact about one repoAGENTS.md or docs/knowledge/ in that repoRepo CODEOWNERS
Stack pitfall or patternknowledge/<stack>/, then the stack skillStack guild
Workflow gapsdlc-core skills or rubricPlatform team
PRD gapstandards/prd-template.md, the rubric, prd_lint.pyProduct ops

The seed entries in knowledge/ show each rung. KB-airflow-0001 (interval-based idempotent writes) was promoted to the Airflow skill. KB-frontend-0001 (no request without access) was promoted to a security rule. KB-process-0001 (PRDs must state unhappy paths) was promoted to lint rule PRD-050. Every entry has a review_by date; a weekly job runs aisdlc.py knowledge-audit and opens an issue for stale entries.

Both sides learnThe product side compounds too. Each story's prd-review.json records why the PRD bounced, and the most common reasons become template prompts and product-owner coaching. This is the same idea as Block's "turn repeated model failures into linters" and Every's compound-engineering step, applied to requirements as well as code.

Each plugin is versioned with semver. Patch releases are wording; minor releases add a skill or check; major releases change a gate. tests/test_manifests.py fails the build if the Claude manifest, the Cursor manifest and the marketplace disagree. claude plugin tag cuts the release. CODEOWNERS give each stack pack to its guild.

Security model

  • Least privilege by stage. Analysts and reviewers are read-only. Connectors are read-only against local or dev data. The builder writes only to its own branch. PR creation is gated. Only people merge.
  • Untrusted input stays data. PRDs, tickets, logs and records never become instructions, and no single stage holds private data, untrusted content and an outbound channel together.
  • Deterministic floor. Hooks block secret reads and writes, force-pushes, merges, infrastructure and cluster changes, writes to data stores, curl | sh, and environment dumps. Claude Code's guards fail closed.
  • Org policy. Managed settings allow only this marketplace and the vetted MCP server commands and URLs, forbid bypass mode, and export telemetry.
  • Audit trail. OpenTelemetry events, the Atlassian MCP audit log, git history of specs and evidence, CI run links, and artifact attestations.

What the data says

  • DORA 2025 (about 5,000 respondents): 90% use AI; it amplifies existing strengths and weaknesses. Small batches, quality internal platforms and AI-accessible internal data predict good outcomes.
  • METR: experienced developers were 19% slower in 2025 while believing they were faster; the 2026 update shows −18% time (CI −38% to +9%). Measure against a baseline.
  • Faros AI (vendor): more PRs and much longer reviews; incidents per PR rose in 2026 Q2. Review is the bottleneck.
  • CodeRabbit (vendor, 470 PRs): AI-co-authored PRs had about 1.7x more issues. An independent review is needed.
  • SWE-bench, UTBoost, ImpossibleBench: validation needs fail-to-pass tests; weak tests pass wrong patches; models modify tests to pass.

What doesn't work

  • Building the orchestrator first. It means months of infrastructure before learning whether specs, gates and evidence work for your teams.
  • One agent, one giant prompt, no gates. Agents drift from specs and overreach (Spotify, Böckeler). Use a deterministic skeleton with agent steps.
  • Prose-only rules for things that must hold. Use hooks and CI checks. The spec-gate eval shows the difference.
  • Letting agents change tests to get green. Block skip markers, require fail-to-pass, and have a separate reviewer check test semantics.
  • Unbounded retries. Cap them (3 per task, 2 verify rounds) and escalate with what was tried.
  • Optimising for "% AI code" or PR count. Instability and review time rise. Measure lead time, rework and escaped defects.
  • Large PRs. Keep one story per branch, about 200-line tasks, and a PR per repo.
  • MCP for everything; ever-growing instructions. Use CLIs for local tools, keep always-on rules near 50 lines, and put the rest in path-scoped skills.
  • Production data in prompts. Use snapshots, read-only dev databases and synthetic fixtures.
  • Auto-merge before the pilot proves quality. Even Meta's RADAR auto-lands only pre-selected low-risk diffs after ML risk scoring.
  • Skipping the baseline. Perceived speed-ups differ from measured ones (METR).
