PRD to PR Playbook

How a Confluence PRD becomes a reviewed pull request with test evidence, with Claude Code, across the Airflow data repo, the micro-frontends and the frontend shell. The recommendation

  1. Use Claude Code as the platform. It already provides sandboxing, permissions, subagents, hooks, MCP connectors, plan mode, worktrees and headless CI. Package the process as one versioned plugin marketplace that every repo enables. Build a custom orchestrator later, and only if volume demands it.
  2. Follow the six-stage loop. Plan, Design, Build, Test, Deploy and Maintain, as in Anthropic's AI-native SDLC playbook. Each stage commits a file to specs/<KEY>/ that the next stage reads: intent.md, spec.md, plan.md, the evidence, the PR. The git history is the audit trail.
  3. People decide at the gates; hooks enforce them. The product owner accepts the intent, a human approves the spec, the engineer (or the tech lead for risk: high) accepts the plan, code owners merge and the release manager authorises production. Agents can't make any of these decisions: the hooks refuse.
  4. One builder, specialised per repo. Each repo declares its stack and commands in .ai/repo.yaml; the Airflow, frontend or MFE skill loads automatically by file path.
  5. Evidence is computed, not claimed. Tests are named after acceptance criteria, new tests must fail without the change, the diff must match the plan, locked tests can't change, and CI re-runs and attests it all.
  6. Start with one repo per stack and measure. Two weeks on setup 1, compared with the last 20 comparable stories, before automating anything. Lead time, rework and escaped defects are the measures.

The loop and its gates

Building is no longer the slow part of delivery; the human-speed steps around it are. The loop keeps those steps but moves them onto files the agent and the people both read, and puts a deterministic check behind every decision that must hold.

What goes where

Ask two questions about a piece of guidance: must it hold every time, and who needs it, when? Advisory mechanisms (CLAUDE.md, rules, skills, subagents) make the right thing likely. Enforced mechanisms (hooks, scripts, CI checks, policy) make the wrong thing impossible or visible.

Not every surface loads everything

Repo-declared plugins install in the terminal, the IDE, the desktop app, GitHub Actions (the plugins input) and the Agent SDK (the plugins option). They don't install in web sessions, scheduled tasks or Claude in Slack, and Slack sessions don't run repo hooks or load .mcp.json. For those surfaces, tools/aisdlc.py vendor copies the skills, agents, scripts and hooks into the repo's .claude/ and writes the rules to .claude/rules/. Wherever hooks can't run, the CI required checks and branch protection are the gate, because they act on the pull request wherever it came from.

One builder, three repos

The builder is one subagent with one discipline: test-first, small commits, stop when stuck. Its stack expertise comes from versioned packs the repo selects, so a developer who mostly writes React can ship an Airflow change with the same guardrails, because the Airflow conventions, tests and checks arrive with the repo.

  • The manifest. .ai/repo.yaml declares the stack, the check commands, how to run given test files, the JUnit paths, protected paths, plan exclusions and production release patterns. Hooks, scripts, agents and CI read the same file.
  • Path-activated stack skills. airflow-dag loads on dags/** and include/**; stack-mfe depends on stack-frontend, so an MFE repo gets both.
  • Session context. At start, resume and after compaction, the SessionStart hook injects the stack, the checks, the branch's Jira key, the state of intent, spec and plan, the evidence state and the rules.
  • Stories across repos. The spec's repo-impact table sets the order: producers before consumers, each step backward compatible. Each repo gets its own branch, plan section, evidence and draft PR; evidence.py judges each repo only on its own row of ACs.

Plan: the PRD gate and the intent

prd_lint.py checks the same things every time: 15 sections (9 required), placeholders, Given/When/Then criteria covering every requirement, vague terms without numbers, NFRs without numbers, missing error, empty and no-access states, and unresolved open questions. The read-only prd-analyst subagent adds judgement: contradictions, roles and data scope, unhappy paths, data feasibility against schema snapshots, hidden cross-team scope and past incidents in the area.

On the example PRD, version 8 scored 16/100 with 3 blocking findings and 13 advisory ones. The product owner got concrete questions with proposed defaults they could accept in one word. Version 9 scored 97/100 and was READY.

  1. The product owner labels the PRD ready. Confluence Automation sends repository_dispatch to GitHub.
  2. ai-prd-intake fetches that page version as Markdown, lints it and runs the review headlessly with a typed verdict.
  3. NEEDS_CLARIFICATION: a Confluence footer comment with the questions, a "Clarify PRD" Jira task for the product owner, and the epic moved to Needs Clarification. The gate re-runs on the next page version.
  4. READY: intent.md is written from the PRD (problem, outcome, affected users and systems, constraints, open questions), linked to the exact page version, and the design stage starts in the same draft PR.

Intents also come from places other than PRDs: a Jira bug, a Sentry issue, a breached control band or a Slack thread. The triage skill writes those, with status: draft until their owner accepts them.

Committed schema snapshots come first; live connectors only fill gaps, and record values never enter the conversation. PRDs, tickets, logs and rows are untrusted data, never instructions, and no stage holds private data, untrusted content and an outbound channel at once.

The spec numbers requirements (FR-n) and acceptance criteria (AC-n), writes every AC as Given/When/Then with one observable outcome, designs only what changes, sequences the repos, plans one qualified test name per AC, sets a risk tier, and lists flagged concerns with their policy owners. A small, low-risk change takes the fast lane: summary, ACs, repo impact and test plan only. The gates stay the same.

Build: the plan, then the code

Work starts in plan mode, where Claude can read the codebase but not change it. The plan skill writes plan.md: the files that change (grouped by repo), the order of work as test-first tasks, the risks and the options not chosen, the proof for each AC, and any locked tests. It iterates until an engineer who never saw the conversation could implement the change from the plan alone.

  • Acceptance. The engineer accepts routine plans in plan mode; for a risk: high spec the tech lead does, and the hook stops the agent accepting it. In CI, routine plans are accepted as auto mode for routine work.
  • The builder loop. Load the stack skill, write the failing tests with qualified AC names, see them fail for the right reason, implement the minimum, run the checks, commit one task at a time and tick it in the plan. Three attempts per task, then stop and report.
  • Locked tests for bug fixes. Reproduce the bug as a test, commit it alone, lock it with evidence.py lock, then fix the code. The hooks block edits to locked tests and evidence.py fails if their content changes, however it was edited.
  • Parallel work. Tasks that touch different files run in separate worktrees (claude --worktree); start with two or three and add more only while review keeps up.
  • Plan drift. When the work departs from the plan, the plan changes in the same commit. Evidence is incomplete while the diff touches a file the plan doesn't list.

Test: evidence and agent evals

evidence.py run runs the manifest's checks with hashed logs; links JUnit test names to this repo's ACs; runs new and changed tests on the merge-base to prove at least one fails there (strong when it fails on an assertion, weak when it only errored); checks that the plan is accepted, lists every changed file and that locked tests are unchanged; and writes a manifest for the commit on a clean tree. PASS is the only verdict that opens a PR.

LevelWhat happensWho trusts it
1 LocalThe verify skill runs the evidence at a committed SHA; the qa-verifier subagent checks the tests prove their ACsThe PR hooks
2 CI re-runai-evidence re-runs the same script at the PR head on a clean runner, adds changed-line coverage, comments the verdictBranch protection (required check)
3 AttestedThe evidence bundle is uploaded and attested with Sigstore, tied to the commitReviewers and auditors

Agent evals. CLAUDE.md, skills, hooks and the plugins steer the agent, so they get regression tests too. Each repo keeps 20 to 50 real tasks in evals/ (a prompt plus the checks that define acceptable). agent_evals.py runs each in a fresh worktree with claude -p; ai-agent-evals runs them on every change to that configuration and nightly, and fails below an 80% pass rate. Every production incident adds an eval. The standard's own skills are tested the same way with claude plugin eval, including a no-plugin baseline.

Deploy: review, approval gates and CI/CD

  • Review on every PR. REVIEW.md defines three passes (bugs, security, compliance with the spec and plan), what Important means, a cap of five nits, and what not to report. The managed Claude Code Review reads it; the ai-review workflow does the same with claude-code-action. Findings never approve or block.
  • The fix loop. @claude on a PR comment makes Claude address it and push to the PR. pr-babysit sweeps failing checks and open threads until only code-owner approval is left, and never merges.
  • Approval gates as hooks. Draft PRs only; no merges; no pushes to protected branches. Production release commands are blocked unless the release manager has set RELEASE_APPROVAL for the session, and even then each one asks. Non-negotiable hooks go in managed settings, where developers can't switch them off.
  • CI/CD. Claude starts with read-only judgement steps: ai-evidence triages its own failures and comments. Anything Claude writes arrives as a PR through branch protection. Deployments are exposed per environment, and production stays behind the release manager.

Maintain: closing the loop

Detection stays deterministic. bands.py keeps a rolling baseline of a metric (by default the CI test failure rate) and applies the Western Electric rules; .ai/bands.yaml sets what each tier allows:

Running it in an enterprise

Distribution and updates

Plugins update automatically from the marketplace (running sessions need /reload-plugins). Vendored repos re-run aisdlc.py vendor and review the diff; the version is pinned in .claude/aisdlc/VERSION.json. CI workflows pin AISDLC_REF to a release tag. Each plugin uses semver: patch for wording, minor for a new skill or check, major for a changed gate. CODEOWNERS give each stack pack to its guild.

Two policy tiers

policy/managed-settings.json registers the marketplace, force-enables the core plugins, allows only this marketplace and the vetted MCP servers, forbids bypass mode, sets a minimum Claude Code version and exports telemetry. managed-settings.regulated.json adds managed-only permission rules and hooks, an OS sandbox that refuses to start when unavailable, an egress allowlist, credential isolation and no side-loaded plugins.

Security model

  • Least privilege by stage. Analysts and reviewers are read-only; connectors are read-only against local or dev data; the builder writes only to its own branch; PR creation is gated; only people merge and release.
  • Untrusted input stays data. PRD, ticket, log and record text never becomes instructions.
  • A deterministic floor. Hooks block secrets, force-pushes, merges, infrastructure and cluster changes, data-store writes, curl | sh, environment dumps and unapproved releases, and fail closed.
  • Workflows that untrusted users can trigger hold no secrets beyond what the action needs.
  • Audit trail. The artifact chain in git, CI run links, attestations and OpenTelemetry events.

Cost

Measured with claude plugin details on Claude Code 2.1.308, the always-on context cost is about 1,763 tokens for sdlc-core, 278 for the connectors and 149 to 181 per stack pack. Skill and agent bodies load only when used. A behavioural eval session cost $0.05 to $0.11; the full suite, 3 runs per arm with the baseline, cost $2.13. Track cost per merged PR from OpenTelemetry.

What doesn't work

  • Building the orchestrator first: months of infrastructure before learning whether the gates and evidence work.
  • One agent, one giant prompt, no gates: agents drift from specs. Use a deterministic skeleton with agent steps.
  • Prose-only rules for things that must hold: without the plugin, Claude wrote code past the spec and plan gates in 6 of 6 eval runs; with its hooks, in none.
  • Letting agents change tests to get green: block skip markers, lock bug-fix tests, require fail-to-pass.
  • Unbounded retries: cap them and escalate with what was tried.
  • Optimising for the share of AI code or PR counts: instability and review time rise.
  • Large PRs: one story per branch, small tasks, a PR per repo.
  • Ever-growing instructions: keep CLAUDE.md under a page and always-on rules near 50 lines.
  • Production data in prompts: use snapshots, read-only dev databases and synthetic fixtures.
  • Auto-merge before the pilot proves quality, and skipping the baseline.

What was verified

In this repository, 22 October 2026

  • Pass 98 unit tests on Python 3.9 and 3.13: PRD lint, AC coverage, fail-to-pass in throwaway git repos, evidence (including plan drift and locked tests), the agent-evals runner with a stub CLI, control bands, every hook (including the plan gate, locks and release gate), the Atlassian client, schema snapshots, the onboarding CLI and manifest consistency.
